# serve-net v0.2.0 - Design Lock

**The API, written down before the code.** v0.2.0 locked the public API of serve-net from `0.3.0` to `1.0.0`: every type, trait, function, error, limit, and default, with the version that ships each one, reconciled with net-io's own 0.2 design lock. There is still no functional code in this release; `0.3.0` is the first working server.

## What is serve-net?

The engine a network service runs on. It takes listeners from net-io, learns the real client behind any front end, runs a sans-IO protocol engine over each connection, and hands one normalized request at a time to a service. It owns request deadlines, keep-alive, limits, admission under load, drain, restarts without dropped connections, and readiness. HTTP/1.1 through http-net is the first engine; FastCGI, WebSocket, and custom protocols use the same slot.

## What's in 0.2.0

- `docs/API.md`: every public item with its signature, behaviour, errors, cost target, and examples, graded P0 to P3 and sorted into three tiers. The simplest use is one call: `serve_net::http("127.0.0.1:8080", |req, reply| { reply.text(200, "hello"); })`.
- serve-net's scope changed: it is the public, generic engine that applications wrap. The fixed security pipeline and the service core left its scope (the wrapping application builds them on serve-net's hooks), the connection gate is installed on net-io, and CGI mode was dropped in favour of persistent processes and FastCGI.
- The division of work with net-io was settled: net-io owns accepting, worker threads, the door, transport deadlines, hard caps, kill, and drain mechanics; serve-net's per-connection engine is a net-io session that adds request deadlines, keep-alive, admission, and the hand-off order. serve-net uses net-io's control line, lanes, gate, event sink, and trusted-proxy list rather than second copies of them.
- Admission was settled as two tiers: soft connection caps answered with `503` and a jittered `Retry-After` before anything is read, and net-io's hard caps above them; then an in-flight cap per worker and per profile after the head is complete, with priority lanes.
- `dev/PLAN.md` recorded the requirements, 40 threats each with its defence, test, and cost, 26 validation rules that refuse insecure configurations at start-up, the performance targets, the testing plan, the enterprise and distributed requirements, the upstream requests, and decisions D-006 to D-035.
- `dev/ROADMAP.md` followed the portfolio's version table and records the net-io version each serve-net version needs.
