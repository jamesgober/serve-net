# serve-net v0.6.0 - Upgrades

**WebSocket on the same listener, and less work per request.** v0.6.0 adds WebSocket upgrades over ws-net, a CI run under real systemd, and a performance pass that cuts serve-net's own work per keep-alive request by about a fifth, with every target's status in `docs/PERFORMANCE.md`.

## What's new

- **WebSocket upgrades** (feature `ws`). A service answers `head` with `HeadAction::Upgrade(WebSocketTarget::new(service).into())`; ws-net checks the handshake, http-net writes the 101, and the `WebSocketService` is called on the worker once per complete message with a `WebSocketConn` to reply through. Every message passes the control line and the checkpoint like a request, so a session revoked while a socket is open stops at its next message (1008), a drain closes with 1001, and lockdown or shedding with 1013. Frames are capped at 64 KiB and messages at 1 MiB by default, output is bounded per connection (`WsSendError::Full`), and a quiet socket is pinged and then closed. Bytes after the upgrade request go to ws-net, never to the HTTP parser. `examples/websocket.rs` is an echo page.
- **systemd in CI.** `examples/systemd.rs` runs as a transient `Type=notify-reload` unit with a watchdog, reloaded ten times under 2,000 keep-alive requests: every answer 200, every reload confirmed by systemd, a clean drain on stop. The wrapper script shows how to map `SIGHUP` and `SIGTERM` to `reload` and `drain`.
- **Faster request path.** The request path no longer clones the server's shared state for every request (six reference-count updates on one cache line that every worker writes), and release builds no longer read the clock around every service call. A keep-alive GET on the test transport went from about 308 to 267 ns; serve-net's own share is about 172 ns.
- **`docs/PERFORMANCE.md`.** The method, the hardware, and each performance target's status, met or not.

## Fixed

- **A CI script that could hang.** A local run of the new systemd job looked stuck for over 280 s. A stale failed unit had left the user manager reporting `degraded`; the script took that for "no user manager", fell back to `sudo`, and sudo's password prompt under `timeout` stopped the job with `SIGTTIN`, where a timeout cannot end it. The script now counts any manager state as up, runs `sudo -n` (it fails instead of prompting), and puts a time limit on every call; every CI job has a time limit too. The same run found that the default `KillMode` sent the stop signal to the server directly, so it never drained; the unit now uses `KillMode=mixed`. No test and no library code was involved.

## Known issues

- **Restarts on Windows (T-30).** The guarantee that a restart through a shared socket refuses and resets nothing is tested on Linux and macOS only. Plan a Windows restart around a front end that retries. Open until fixed, at the latest before any 1.0 release candidate.
- **Request path cost.** serve-net's own work per keep-alive request is about 172 ns against a 150 ns target, and the 3-entry forwarded walk 137 ns against 100 ns. Both are in the pre-1.0 performance pass.
- **Throughput against other servers is not measured.** The target (20% above hyper with hyper-util) needs a load generator on separate hardware. This blocks 1.0.
- **Idle memory.** About 9 KB per idle keep-alive connection against 4 KiB; waits on net-io 0.6.0.
- **WebSocket limits.** A `WebSocketService` sends only from inside its own calls, and a drain closes an open socket without a Close frame; both wait on net-io 0.6.0. A wiping profile does not zero ws-net's buffers. A gate that denies the upgrade request after the 101 is decided closes the connection instead of answering 403.
- **Low descriptor limits.** With no `max_connections` and a low `ulimit -n`, connections past the limit are reset rather than answered 503.
- **An injected clock on the reactor.** With a manual clock, a drain on the reactor does not finish; real clocks are not affected.
- **`dedicated_workers` on the reactor** keeps connection seats, not threads.

Each is tracked in the pre-1.0 polish register in `dev/ROADMAP.md`.

## Upgrading from 0.5.0

`HeadAction` is `Clone` and no longer `Copy` or `PartialEq`, because `HeadAction::Upgrade` holds its target: clone it where it was copied, and match it where it was compared. `HeadAction` and `RequestEnd` gain a variant each (`Upgrade`, `Upgraded`); both are non-exhaustive. `Family` gains a provided `upgrade` method and `Service` and `HttpService` a provided `upgraded`, so existing implementations compile unchanged. The `ws` feature adds ws-net 0.2 as a dependency; without it nothing changes.
